# Spike 002 — Синхронизация планера ученика и преподавателя без перезагрузки страницы

Дата: 2026-10-16. Источник: фидбек Мурада. Раньше планер был таблицей в Google Sheet, и правки были видны сразу. Хочет того же:
Мурад добавил задания, ученик сразу их видит. Ученик поставил галочку или написал в дневник, Мурад сразу это видит.

Условие спайка: если для этого нужно переделывать Payload или есть сложности на Vercel, не делаем.

## Вывод

**Реально, на текущем стеке, без переделки Payload и без новой инфраструктуры.** Рекомендую вариант A: опрос лёгкой
«ревизии» планера раз в ~5 с и обновление страницы, когда ревизия изменилась. Задержка в среднем ~2,5 с, максимум ~5 с.
Настоящий push (меньше секунды) на Vercel возможен только через сторонний сервис (вариант B). Сейчас это дороже, чем даёт.

Главная стоимость не в транспорте. Клиентские компоненты планера сейчас не умеют принимать чужие обновления, их нужно
переделать (раздел «Что мешает сейчас»). Оценка: ~2–3 дня и два PR.

## Профиль нагрузки

- 20–35 учеников, у каждого один планер, смотрят его 2 человека (ученик и Мурад).
- Правки редкие: поставить галочку, написать задание, записать в дневник.
- Нагрузка маленькая, масштабировать нечего. Решает простота и эксплуатация, а не пропускная способность.

## Кто что пишет

По `src/features/planner/service.ts` и `src/collections/Planner*.ts`:

| Кто    | Что пишет                                                                                                     |
| ------ | ------------------------------------------------------------------------------------------------------------- |
| Мурад  | текст ячеек, строки и недели, подписи и типы заданий                                                          |
| Ученик | `done`; записи дневника (`planner-notes`); текст ячейки, если у планера заданы типы заданий (выбор из списка) |

Поля почти не пересекаются, конфликты редки. «Последняя запись побеждает» остаётся приемлемой, отдельной схемы
слияния на сервере не нужно. Все записи идут через Local API в `service.ts`, поэтому Payload не меняем.

## Что мешает сейчас

- `PlannerGrid`: `useState(initial)`, а текст ячейки — `<textarea defaultValue>`. После `router.refresh()` новые данные
  не попадут ни в состояние, ни в поля.
- `EditableText` (дневник, подписи): `useState(value)` и `saved`. Та же проблема.
- `PlannerBoard`: `live = useState(grid.cells)` для прогресса, ключ `${week.id}-${rowCount}`.
- Мурад может удалить строку или неделю, пока ученик на ней. Сохранение вернёт `not_found` или `invalid_input`, это нужно
  показать понятно.

Нужна схема «серверный снимок + локальная правка поверх»: поле в фокусе или с несохранённым текстом не перезаписываем,
чужое значение применяем после blur.

## Варианты

| Вариант                                                      | Задержка | Вердикт        |
| ------------------------------------------------------------ | -------- | -------------- |
| **A. Опрос ревизии + `router.refresh()`**                    | 0–5 с    | **Рекомендую** |
| B. Managed pub/sub (Pusher, Ably): push «сигнала» без данных | <1 с     | Запас на потом |
| C. Свои WebSocket или SSE на Vercel Functions                | <1 с     | Нет            |
| D. Postgres `LISTEN/NOTIFY`                                  | <1 с     | Нет            |
| E. Neon Realtime (live SQL)                                  | <1 с     | Нет            |

### C. Свои WebSocket или SSE на Vercel

- WebSocket на Vercel Functions в **beta** (на всех тарифах). Next.js не даёт API для upgrade, нужен `upgradeWebSocket`
  из `@vercel/functions`.
- Соединение привязано к одному инстансу и рвётся по `maxDuration`: 300 с на Hobby, 800 с на Pro. Нужны reconnect и
  Redis для рассылки между инстансами.
- SSE проще, но лимит по длительности тот же. Функция занята, пока открыта вкладка, и оплачивается память.
- Сама Vercel в гайде для небольших приложений с редкими обновлениями советует «fetch on demand or poll».

### D. `LISTEN/NOTIFY`

Удерживаемое соединение не даёт Neon уйти в scale-to-zero. Pooler (transaction mode) `LISTEN` не поддерживает. Инстансов
много, и до браузера всё равно нужен транспорт.

### E. Neon Realtime

- Beta, протокол не стабилен, нужна logical replication и клиентская библиотека `@neon/realtime`.
- Живые запросы читают данные в обход Payload access control. Это противоречит правилам репозитория: данные только через
  Local API, библиотеки не добавляем без запроса.
- Payload они не меняют, и подписки не мешают scale-to-zero. Вариант стоит пересмотреть после GA и RLS.

### B. Managed pub/sub

Сервер после записи шлёт событие «планер N изменился» (без данных), клиент по нему делает тот же `router.refresh()`.
Права проверяет Payload, как и сейчас, через сторонний сервис данные не проходят. Цена: новый вендор, ключи в Vercel
env, `connect-src` в CSP (`security-headers.ts`), эндпоинт авторизации приватных каналов. Клиентская часть та же, что в A,
меняется только источник сигнала. Поэтому A не тупик: B можно добавить позже, не переделывая интерфейс.

## Рекомендуемый дизайн (вариант A)

1. **Ревизия планера.** Server Action рядом с `exportPlannerAction` (Zod → `currentUser` → `monitorAction`) и функция в
   `queries.ts`. Четыре лёгких чтения с `overrideAccess: false`, `select: { updatedAt }`, `limit: 1`, `sort: -updatedAt`:
   `planners`, `planner-weeks`, `planner-cells`, `planner-notes`. В подпись входят максимум `updatedAt` и `totalDocs` каждой
   коллекции. **Счётчик обязателен:** `setCellText` с пустым текстом удаляет документ ячейки, и одним `updatedAt` это
   не поймать. Схема БД и миграция не нужны.
2. **Хук `usePlannerSync(plannerId, signature)`.** Опрос раз в ~5 с, пока вкладка видима. На `visibilitychange` и при
   фокусе проверка сразу. Замедление до ~30 с при простое и при ошибках. После смены подписи `router.refresh()`.
3. **Рефакторинг** `PlannerGrid`, `EditableText`, `PlannerBoard`, `PlannerDiary` под «снимок + оверлей».
4. **Индикатор** «обновлено / нет связи» с `role="status"`, тексты в `messages/en.json` и `messages/ru.json`.
5. Без изменений: CSP, env, Payload-конфиг, коллекции, миграции.

## Оценка

Оценки порядка величины, ничего не измерено.

- **Работа:** ~2–3 дня. Два PR (правило «≤400 строк»): (1) рефакторинг «снимок + оверлей» без смены поведения;
  (2) ревизия, опрос, индикатор, тесты.
- **Нагрузка:** ~20 одновременных зрителей раз в 5 с ≈ 4 запроса/с в пике, по 4 лёгких чтения. Опрос идёт только
  пока вкладка видима. Месячное число вызовов нужно сверить с лимитами тарифа `[verify in dashboard]`.
- **Neon:** во время сессий база не засыпает. Ученики и так её будят, заметного влияния на счёт не ожидаю
  `[verify in dashboard]`.
- **Задержка:** в среднем ~2,5 с, максимум ~5 с.

## Риски

- Рефакторинг клиентских компонентов легко сломать: потеря фокуса, каретки или несохранённого текста. Нужны browser-тесты
  слияния снимка с оверлеем.
- `router.refresh()` перерисовывает всю страницу (6–7 чтений в `getPlannerView`). При правках раз в несколько секунд это
  много. Если станет заметно, перейти на загрузку только изменившегося.
- Сохранение собственных правок вызывает лишний `refresh` у автора. Он безвреден благодаря слиянию, но его можно гасить,
  запомнив подпись после своей записи.
- Подпись включает `planners.updatedAt`, поэтому сохранение внешнего вида учеником тоже запускает обновление у Мурада.
  Безвредно: `PlannerShell` держит свой `appearance`.

## Решения владельца (2026-10-16)

- Задержка до ~5 с устраивает.
- Тариф Vercel: **Hobby**. Опрос укладывается в лимит 300 с на вызов, долгих соединений нет. Месячное число вызовов
  сверить с лимитом тарифа `[verify in dashboard]`. Hobby рассчитан на некоммерческое использование: для платных занятий
  это стоит проверить в условиях Vercel `[verify]`.
- Интерактив пока только на `/study/planner`. `day-comments` программы на `/study` не затрагиваем.
- «Собеседник сейчас на странице» (присутствие): нужно, если не слишком сложно. Опросом это не сделать, нужен
  Pusher или Ably. Вынесено в отдельную историю 033 (`docs/stories/033-planner-presence.md`), чтобы не блокировать 032.
  Порядок: 032, затем 033.
